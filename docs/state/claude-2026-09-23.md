## 1. "Pictures on samoshop take so long" — three causes, the biggest outside the shop

Measured on production with headless Chrome (390 px, DPR 3, cache off), by
phase: opening /shop **~47 MB**, a product popup **~16 MB**, the zoom **~6.5 MB**.

- **45 MB was news pictures.** `announcements.js` `pickCover`/`extractSnippet`
  put every post's HTML into a detached `<div>` — which downloads every `<img>`.
  Control run: the same build with only that fix reverted downloaded 14.8 MB in
  9 s. Fixed with `DOMParser` + a sweeping guard.
- **The product masters are 2 MB PNGs** (Safari's WebP fallback kept the
  original). lh3 serves the master's format; `-rw` on PNG is lossless. JPEG
  (`-rj`, lh3 default quality 90) = 40.6 dB PSNR, no visible difference at 2×
  on the pattern's edges; the zoom asks quality 95.
- **Cards asked for the 1200 px cover.**
- The owner then asked for full quality AND speed: lh3's own first byte is
  0.5–2.6 s, so nginx now caches `/img/d/<id>=w…-rj` on the VM (hit ~0.02 s).
  All 28 current picture sizes were pre-warmed.

After (production): grid **212 KB**, popup **1.1 MB**, zoom **~1 MB**, every
picture a cache HIT.

Owner's follow-ups, same day, all fixed and measured per frame:
- the popup showed the cover, then scrolled to the pre-selected colour — now
  placed by a ResizeObserver before the first painted frame (old code in the
  same measurement: positions 0 → 684; new: 684 only);
- a blank blue stage while loading — every slide has a placeholder;
- the admin รายละเอียด box cut text off — `.shop-autogrow` on six shop-admin
  textareas (CSS `field-sizing`, a JS fallback for old Safari — NOT seen on a
  real iPad).
